## Step 3 — Round lifecycle with a scheduled sweeper

**Goal:** `POST /start` begins round 1; the server owns the timer, picks the
drawer and the word, and rolls the game through rounds to completion.

**What was built**

- `WordProvider` — 72-word dictionary; picks a word not already used in the room.
- `Round` entity + `RoundRepository` — durable, per-round history (drawer, word,
  status, timestamps). The room row remains the aggregate root for the *current*
  round; `rounds` is the audit trail.
- `RoundService` — host-only `start` (LOBBY, ≥2 players), round rotation by join
  order, word selection, and round end/finish.
- `RoundScheduler` — `@Scheduled(fixedDelay = 1s)` sweep that advances expired
  rounds. `@EnableScheduling` on the application.
- `RoomStateDto` extended with `currentDrawerId`, `roundEndsAt`,
  `secondsRemaining`, and `currentWord` (returned **only** to the current
  drawer). `ForbiddenException` (403) added.

**Defect found (by tests): `StaleObjectStateException` on the room row.**
The first version swept by loading a list of expired `Room` entities in one
transaction and mutating each. Under the integration suite two Spring contexts
were alive, each with its own scheduler, both sweeping the same in-memory
database. Two transactions could load the same room and both try to write it,
producing an optimistic-lock failure on flush.

**Fix: sweep ids, transition per-room under a fresh lock.** This also hardened
the design for the later V5/V6 multi-instance story:

- `RoomRepository.findExpiredIds(...)` returns only `List<Long>` (no entities
  held across work).
- `RoomService.advanceIfExpired(Long)` runs in its **own transaction**:
  re-reads the room with a pessimistic write lock (`findByIdForUpdate`),
  revalidates that it is still `IN_PROGRESS` and actually expired, and no-ops if
  a concurrent sweep already handled it. The transition happens exactly once.
- `RoundScheduler` iterates ids and defensively catches
  `ObjectOptimisticLockingFailureException`.

**Defect found: flaky `RoundSchedulerIntegrationTest`.** The 1-second-round test
shared the default in-memory H2 database with other live Spring contexts, so its
rooms were swept by more than one scheduler — inherently timing-dependent. Fix:
that context gets its own database
(`jdbc:h2:mem:scribl_sched`). Rotation is asserted from the durable `rounds`
history rather than by catching a fast active-round window. Verified by running
the full suite three times back-to-back.

**Live check (Neon, 2-second rounds):** non-host start → 403; host start → 200;
the drawer saw the word while the guesser saw `null`; rounds advanced
alice → bob → `FINISHED`.

## Step 4 — Append-only drawing ingest and incremental retrieval

**Goal:** `POST /drawing` (drawer only) appends strokes/clears; `GET /drawing?
sinceSeq=N` returns only events newer than the client's high-water mark.

**Schema (migration `V3__drawing_actions.sql`)**

- Added `action VARCHAR(8) NOT NULL DEFAULT 'POINT'` (`POINT` | `CLEAR`).
- Made `x, y, color, size, tool` nullable so a `CLEAR` event carries no geometry.
- **No index added.** The `(round_id, seq)` read path stays unindexed on purpose
  — it is the V2 measurement baseline for the V4 index experiment. Per-round
  `seq` integrity is guaranteed by the application (see below), not an index.

**What was built**

- `drawing/` package: `DrawingPoint` entity, `DrawingAction`, repository,
  `DrawingService`, `DrawingController`, and DTOs.
- `POST /api/rooms/{code}/drawing` — drawer-only, active-round-only. `seq` is
  `max(seq) + 1` for the round, computed in the same transaction and under the
  same pessimistic room lock the sweeper uses, so sequence assignment is
  collision-free without a unique index.
- `GET /api/rooms/{code}/drawing?sinceSeq=N&roundNumber=R` — member-only
  incremental replay, events with `seq > N` in seq order; `CLEAR` events tell
  clients to reset before applying subsequent events.
- `RoomRepository.findByCodeForUpdate` for the write path.

**Cross-cutting improvement:** `GlobalExceptionHandler` now maps
`HttpMessageNotReadableException` (malformed JSON or an invalid enum value) to
**400** instead of falling through to the generic 500 handler.

**Test gotchas worth remembering**

- Entities never receive their id from a constructor; unit tests that exercise
  id-dependent logic need a way to set it. `Round` gained a `setId` (mirroring
  the existing `Room.setId`) purely as a test seam.
- Mockito's strict stubs turn an unmatched argument into `PotentialStubbingProblem`;
  stubs must match the *actual* runtime arguments (this is why the null round-id
  mismatch surfaced loudly rather than silently passing).

**Live check (Neon):** V3 applied; pre-start drawing → 403; non-drawer → 403;
event seqs 1/2/3; full replay showed a `CLEAR` with null geometry;
`sinceSeq=2` → `[3]`; an outsider's token → 401.

## Step 5 — Guessing, scoring, round advance, leaderboard

**Goal:** non-drawers guess; correct guesses score and end the round; standings
are visible.

**What was built**

- `guessing/` package: `Guess` entity (`guesses` table already existed from V1;
  its index was dropped in V2), repository, `GuessService`, `GuessController`,
  DTOs.
- `POST /api/rooms/{code}/guesses` — member-only, non-drawer-only,
  active-round-only. Matching is case-insensitive and trimmed.
- Scoring: a correct guesser earns `100 + seconds remaining` (speed bonus); the
  drawer earns a flat `50` per solve.
- **One transition path.** Extracted `RoundService.completeRound(room)` and made
  both the timer sweep and a correct guess call it, so a solved round and an
  expired round can never diverge.
- `GET /api/rooms/{code}/leaderboard` — member-only standings ordered by score
  (ties keep join order); `LeaderboardDto`.

**V1 simplification (deliberate):** there is no separate "round over" reveal
interlude. A correct guess advances immediately; the outcome is in the guess
response and the next round (or `FINISHED`) appears on the next state poll.
Scores are written in the same transaction as the guess.

**Live check (Neon):** drawer guessing → 403; wrong guess → `{correct:false, 0}`;
correct guess awarded 154 (100 + time); round advanced to 2 and the drawer
rotated; leaderboard showed the drawer bonus (154 vs 50); the final round drove
the room to `FINISHED` (205 vs 204).

## Decisions and invariants reinforced

- **Exactly-once transitions.** Any round transition (timer or solved) loads the
  room under a row lock, revalidates, and is safe against a concurrent sweep.
  This is the local version of the V5/V6 cross-instance contract.
- **Server authority.** Identity, drawer status, word visibility, scores, and
  transitions are all computed server-side; the client is never trusted.
- **The naive baseline is protected.** No index was added for drawing or
  guesses; the unindexed hot paths remain the honest V2 baseline.
- **Migrations are append-only.** V1 and V2 were not edited (Flyway checksums);
  V3 adds the drawing action column. Neon is at schema v3.
